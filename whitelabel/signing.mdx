Signing is how your developer key approves a payment from your integrator account. Open the payment with `POST /dapi/v1/payouts`, sign `approval.payload`, and post the signature to the confirm route.

<Steps>
  <Step title="Prepare" icon="file-text">
    Call the prepare route. The response has `quote`, `approval` and `debit`.
  </Step>
  <Step title="Check" icon="scale">
    Compare `debit` with the payment in your system and stop if they differ. `debit` is decoded from the operation you sign: `amount`, `amountAtomic`, `token`, `chainId` and `address`.
  </Step>
  <Step title="Sign" icon="pen-tool">
    Base64-decode `approval.payload` and sign the decoded bytes in the [signature format](#signature-format).
  </Step>
  <Step title="Confirm" icon="check">
    Post the signature to the confirm route before `approval.expiresAt`. HEVN verifies it against the stored bytes, co-signs and submits.
  </Step>
</Steps>

## Routes

| What moves | Prepare, under `/dapi/v1` | Confirm | Approval window |
| --- | --- | --- | --- |
| Payout from your account: fiat over a bank rail, or USDC on Base to a wallet contact | `POST /payouts` | `POST /payouts/{payoutId}/confirm` | 120 s |
| Swap between two of your accounts | `POST /swaps` | `POST /swaps/{swapId}/confirm` | 120 s |
| Escrow action you operate | `POST /escrow/{escrowId}/actions` | `POST /escrow/{escrowId}/actions/{idempotencyKey}/confirm` | 60 s |
| Payout for a client | `POST /payouts` with `X-Hevn-Account` | None. The holder signs in the [sign-in window](/whitelabel/sign-in-with-hevn#approve-a-payout). | About 10 minutes (the sign-in window session) |

On the signed routes, omit `X-Hevn-Account` or send your `cl_…`. See [Who can spend](/whitelabel/overview#who-can-spend) and [Acting as a client](/whitelabel/authentication#acting-as-a-client).

## Authorization values

`authorization` in the prepare response says who signs. With `debit` and `intent` your developer key signs, and the payload bytes, the confirm route and the retry rules are the same. With `client` the holder signs and no `approval` is returned, so check `quote` and `contact` before you open the sign-in window. With `wallet` an external account sends the transfer, so there is nothing to confirm. Which value a payout or a swap returns, and what to check before signing, is on [Create an outgoing transfer](/api-reference/transfers/create-an-outgoing-transfer) and [Create a transfer between the client's own accounts](/api-reference/transfers/create-a-transfer-between-the-clients-own-accounts).

The confirm body:

```json
{ "signature": "MEUCIQD…", "publicKey": "MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE…" }
```

The field rules are on [Authorize an outgoing transfer](/api-reference/transfers/authorize-an-outgoing-transfer).

HEVN re-checks the key and the source address before it co-signs. A key deleted after the prepare, or a confirm from outside [the IP allowlist](/whitelabel/authentication#the-ip-allowlist), returns `403`.

## Payload

`approval.payload` is base64 of a canonical JSON document. A decoded payout payload, formatted for reading (the real bytes have no whitespace):

```json
{
  "body": {
    "method": "secp256k1_sign",
    "params": { "hash": "0x9c1f7b4a2e5d80c6314fa7b95d0e28c4f61ab3907d5c2e84061bf39d7a2c5e18" }
  },
  "headers": {
    "privy-idempotency-key": "quote-sign:5f3c…e1",
    "privy-request-expiry": "1773679531000"
  },
  "method": "POST",
  "url": "…",
  "version": 1
}
```

Sign `base64decode(payload)` unchanged. Do not parse and re-serialize the JSON. Reordered keys, a space after `:`, different escaping or a trailing newline return `400 signature_invalid`.

HEVN builds the operation from the booking: a single stablecoin transfer from your wallet. The approval is bound to your account, the target, the wallet and your signer.

Prepare refuses a target that is not in a fundable state, a wallet whose on-chain owner is not your signer (`409 signer_not_attached`) and a balance below the transfer (`409 insufficient_funds`). See [Errors](/whitelabel/reference/errors).

## Signature format

| Rule | Value | Common mistake |
| --- | --- | --- |
| Algorithm | ECDSA on P-256, digest SHA-256 | Pre-hashing. Most libraries hash the message. |
| Encoding | ASN.1 DER `(r, s)` | Raw 64-byte `r‖s` (WebCrypto, Java's `SHA256withECDSAinP1363Format`). Convert it to DER. |
| Transport | base64, standard alphabet, padded | base64url (`-` and `_`), or missing `=` padding. |
| Content | One signature, with no `,`, `\n` or `\r` | Signing the base64 text and not the decoded bytes. Base64 wrapped at 64 columns. A newline appended by a shell pipeline. |

A signature that breaks a rule returns `400 signature_invalid` and does not consume the approval. Sign on your server and not in a browser.

## Approval lifetime

An approval is single-use and ends at `approval.expiresAt`. The windows are in [Routes](#routes).

- Run the steps in one pass. A payload queued for a person to approve later expires.
- To re-open, call the prepare route again with the same `Idempotency-Key`. While the payment has not moved, it returns a new approval on the same booked payment, at the same price. A payout that already moved comes back with no `approval`.
- Re-opening has no attempt limit. Each new approval uses the same on-chain slot. See [Why a retry cannot pay twice](/whitelabel/conventions#why-a-retry-cannot-pay-twice).

## Retrying a confirm

The first confirm with a valid signature uses the approval. A second confirm on the same approval is refused, so read the payout or swap instead of confirming again. A payout confirm returns `200` when the operation lands within the request, and `202` with `pollUrl` otherwise. A swap confirm, and a payout confirm with `authorization: intent`, always return `202`. An escrow confirm repeated with the same path key returns the first result.

| Response | Meaning | Next |
| --- | --- | --- |
| `200` `status: "settled"` | Done | Store `transactionHash`. |
| `200` `status: "failed"` | The operation reverted on chain. | Book a new payment with a new `Idempotency-Key`. A re-open of this one returns `payment_slot_consumed`. |
| `202` `status: "submitted"` | Sent, no receipt yet | Read `pollUrl` until `status` is `settled` or `failed`. |
| Timeout or network error | Unknown | Read the payout or swap. If `status` is `awaitingSignature`, re-open with the same `Idempotency-Key`. |
| `503` `user_operation_rejected` or `user_operation_unavailable` | The operation was not accepted, or its state could not be read. | As for a timeout. |
| `503` `bundler_rejected` or `bundler_unavailable` | An escrow action was rejected, or the chain was unreachable. | Confirm the escrow action again with backoff. |
| `409` `funding_attempt_expired` (payout with `debit`), `410` `approval_expired` (payout with `intent`), `409` `swap_not_confirmable` (swap) | No open approval: it expired, or a confirm already used it. | As for a timeout. |
| `409` `funding_in_progress` | An attempt is live. | Wait, then send the same call again. |
| `409` `already_funded` | A swap re-open found that the money moved. | Success. Read `details.transactionHash`. |
| `409` `payment_slot_consumed` | An operation for this payment already landed or reverted. | Stop re-opening. Read the payout and book a new one if it is `failed`. |
| `400` `signature_invalid` | Wrong bytes, wrong encoding, or a key that is not on your account. The approval stays usable. | Fix the signing and confirm again. |

Each approval for one payment uses the same on-chain slot. If an earlier operation lands after a re-open, the new one returns `payment_slot_consumed`. The loop as code is in [HTTP client](/whitelabel/reference/client).
