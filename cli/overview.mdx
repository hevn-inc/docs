The CLI drives a HEVN account from outside the app — balances, contacts, invoices, contracts, cards
and transfers. It was built for AI agents and scripts first, so every command can emit a machine-readable
envelope; the human tables are the convenience layer on top.

One credential covers all of it. `hevn login` issues an app API key and saves it locally; nothing
else needs configuring before the first useful command.

## Command shape

Almost every command reads the same way: a resource, then an action.

```bash
hevn [global-options] <resource> <action> [options]
```

Global options go before the resource:

```bash
hevn --env dev account get
hevn --base-url https://api.example.com/api/v1 account get
hevn --debug transfer --invoice-id <invoice-id>
hevn --dry-run transfer --invoice-id <invoice-id>
hevn --non-interactive --yaml contacts list
```

`--json` and `--yaml` also work per command, which is what a script or an agent should reach for.
In structured mode a success is wrapped as `ok`, `data`, `meta` and `warnings`, and a failure as
`ok`, `errorCode`, `errorType`, `error` and `exitCode` — so a caller branches on `errorCode` and
never on a printed message.

Two commands describe the CLI to a machine rather than doing anything: `hevn --schema` prints the
full command manifest, and `hevn agent-skill` prints the packaged operating guide. An agent should
read both before it plans a workflow.

## Authentication

An **app** is a named integration workspace inside a HEVN account. Each app has its own API keys
and, optionally, its own transfer allowance.

`hevn login` opens HEVN in a browser, creates or selects an app, issues an app API key and saves it
to the local config. Automation can skip the browser and save a key it already holds:

```bash
hevn login --api-key hvn_...
```

That one `hvn_…` key authenticates every command, transfers included, and travels in the
`X-Api-Key` header.

The key is more than a bearer token. It is a full EVM keypair, and what it may spend is governed on
chain by a spend permission the account owner granted to its address — so a leaked key is capped by
the remaining allowance for the current period and is revoked on chain, not by a flag in a database.
See [how API keys work](/general/authentication#api-keys-cli-rest-api-agents).

<Note>
  App API keys are the CLI and agent credential. They are **not** the credential for the
  [whitelabel REST API](/api-reference/overview), which authenticates with a developer key and JWT
  sessions and rejects `X-Api-Key`. Transfer commands take no app id: the backend resolves the
  owning app from the key.
</Note>
