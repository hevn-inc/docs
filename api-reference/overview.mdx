## Servers

| Environment | Server | Notes |
| --- | --- | --- |
| Production | `https://api.hevn.finance/v1` | Real money, Base. |
| Sandbox | `https://sandbox-api.hevn.finance/v1` | Test funds, Base Sepolia, one emulated partner. |

The base URL already carries the version, so every path in this reference is relative to it: a full
URL is `https://api.hevn.finance/v1/banks`. The two servers are separate deployments with separate
accounts, and a token issued by one is refused by the other. Pick the server in the playground's
dropdown before you send a request.

The four operations tagged **Sandbox** declare the sandbox server only; production answers `404` for
them. The other 44 exist on both.

## The bearer model

Every operation but the three under **Authentication** takes one header:

```http
Authorization: Bearer <accessToken>
```

The access token is a short-lived JWT your backend mints for itself by signing a challenge with your
developer key. That bearer is the only credential this API documents: `X-Api-Key` belongs to the
[CLI](/cli/overview), is scoped by its own app, and can never authorize money — a key acting for one
of your clients is clamped read-only and answers `403 account_read_only` on any write.

To act for one of your clients, send that client's id in a second header instead of minting a second
token:

```http
X-Hevn-Account: cl_7YQ2Kf3mN8
```

Operations that are about your own account by definition — `POST /clients`, `GET /clients` and all of
**Escrow** — refuse the header with `400 account_scope_conflict`.
Operations that already name a client in the path accept it only when it agrees with the path. The
three under **Authentication** ignore it: a login has no account to act for yet. Each operation
declares which it is in the `x-hevn-acting-as` extension (`self`, `client` or `either`). The full
table is in [Sessions](/whitelabel/sessions#acting-as-a-client).

## One error envelope

Every refusal, on every route, has the same body:

```json
{
  "error": {
    "code": "insufficient_funds",
    "message": "The account's USDC balance does not cover this transfer.",
    "details": { "available": "3000000", "required": "5000000" }
  }
}
```

`code` is a stable lowercase slug — branch on it, never on `message`. Each operation publishes the
slugs it can answer with in the `x-hevn-error-codes` extension, and the whole registry with what to
do about each is in [Errors](/whitelabel/reference/errors). Every response carries an
`X-Request-ID`; quote it in a support request.

## Conventions this reference assumes

Bodies, query parameters and response fields are camelCase; unknown keys are refused rather than
ignored; null fields are omitted, so absent and null are the same thing. Money is always a decimal
string in the asset's major unit (`"500.00"`), never a JSON number. Ids are opaque and prefixed by
what they name. Lists page with a cursor. `Idempotency-Key` is accepted on every write and required
on none. All seven rules, in one page:
[Conventions](/whitelabel/conventions).

## Money movement is signed

Reading data and writing metadata need only a token. Moving money needs a signature from your
developer key, and every such operation is a pair: an opening call that prices and builds the
operation and hands you an `approval.payload`, then a confirm that carries your signature over the
decoded bytes of that payload.

| What moves | Prepare | Confirm |
| --- | --- | --- |
| Fiat out over a bank rail | `POST /payouts` | `POST /payouts/{payoutId}/confirm` |
| USDC out on Base | `POST /transfers` | `POST /transfers/{transferId}/confirm` |
| An escrow deal or action | `POST /escrow`, `POST /escrow/{escrowId}/actions` | `POST /escrow/{escrowId}/actions/{idempotencyKey}/confirm` |

One mechanism, described once in [Signing](/whitelabel/signing).
